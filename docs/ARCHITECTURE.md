# 技术说明

本文说明「打工人决策台」的运行时结构、数据模型、计算口径与失败降级设计。
目标读者是想判断「它到底怎么算的、靠不靠谱」的人。

---

## 1. 四个设计约束（以及为什么）

| 约束 | 理由 | 代价（已接受） |
|---|---|---|
| **单文件、零外部依赖** | 评委、用户点开就能用；不存在 CDN 挂了、依赖装了没、版本冲突 | 源码 3000+ 行集中在一个 HTML，靠注释分区 |
| **不接大模型** | 每次调用烧积分；评委体验时若额度耗尽或网络抖动，功能直接失效，反而伤「完成度」 | 学习内容靠内置知识库（39 个词条），覆盖不到的词走通用学习框架 |
| **无后端、无埋点、无第三方脚本** | 简历、工资、面试记录都是高敏感数据，本地处理才敢让人真填 | 数据不跨设备；用 JSON 备份手动迁移 |
| **确定性计算必须可验证** | 补偿和个税算错，用户也发现不了，只会觉得「怎么跟到手的不一样」 | 必须维护测试套件 |

第 4 条是硬要求：**凡是能被算出来的，就必须能被断言**。

## 2. 运行时结构

```text
offer-compass.html
├── <style>            全部视觉，无外部字体/图标/CDN
├── <body>
│   ├── .hero          标题与能力标签
│   ├── .tabs          六个标签（role=tab / aria-selected / aria-controls）
│   ├── #demoBar       示例数据引导（首屏可见）
│   ├── .pane ×6       p1 Offer / p2 补偿 / p3 年终奖 / p5 JD / p6 复盘 / p4 小抄
│   ├── #stOv          计算器自检弹层
│   ├── #bkOv          数据备份弹层
```

函数声明提升保证了这种书写顺序可用，实际调用全部发生在用户交互之后。

## 3. 数据模型与存储键

全部数据在 `localStorage`，键名带版本后缀，便于将来迁移。

| 键 | 类型 | 结构 | 写入时机 |
|---|---|---|---|
| `wdc_offers_v1` | JSON 数组 | `{name,sal,mon,bon,fund,eq,ot,cm}` 全为字符串（保持输入原样） | 输入后 300ms 防抖 |
| `wdc_interviews_v1` | JSON 数组 | `{co,pos,date,round,cat,q[],note,ts,sample?}`，`q` 为被问住的点数组 | 点「保存这条复盘」立即写 |
| `wdc_resume_v1` | 字符串 | 简历原文 | 输入后 400ms 防抖 |
| `wdc_jd_v1` | 字符串 | 最近一份 JD 原文 | 输入后 400ms 防抖 |

**备份文件格式**（`exportAll` 生成）：

```json
{
  "app": "wdc-backup",
  "version": 1,
  "exportedAt": "2026-10-22T01:20:00.000Z",
  "data": { "wdc_offers_v1": "[...]", "wdc_resume_v1": "..." }
}
```

导入时依次校验：能否 JSON 解析 → `app` 字段是否等于 `wdc-backup` → `data` 是否存在。
任一不符直接拒绝且**不写入任何键**，避免用半个坏文件覆盖好数据。

存储值统一存原始字符串而非数字，理由是回填表单时不必处理「0 与空」的歧义；
所有数值转换集中在 `num()` / `+value` 处一次完成。

## 4. 计算口径

四个纯函数承担全部计算，界面只做取值与渲染。这使得页面自检、Node 测试、线上运行共用同一份实现。

### 4.1 `compMonths(din, dout)` → 工龄月数

按「满月」计算：先算年月差，若离职日小于入职日则减 1 个月。日期倒挂或同一天返回 `-1`（非法）。

```text
2020-03-10 → 2026-09-20  ⇒  (2026-2020)*12 + (9-3) = 78 个月（6 年 6 个月）
2020-03-10 → 2026-03-09  ⇒  71 个月（差 1 天不满 6 年，按 5 年 11 个月计）
2024-02-29 → 2025-02-28  ⇒  11 个月（闰日边界）
```

### 4.2 `nOfM(months)` → 经济补偿月数 N

依据《劳动合同法》第 47 条：每满 1 年支付 1 个月；满 6 个月不满 1 年按 1 年；不满 6 个月支付半个月。

```text
rem = months % 12
N = floor(months/12) + (rem >= 6 ? 1 : rem > 0 ? 0.5 : 0)

5 个月 → 0.5 ｜ 6 个月 → 1 ｜ 78 个月 → 7
```

### 4.3 `bonusTaxInfo(bonus)` → 年终奖单独计税

**这是全项目最容易写错的一段。** 正确做法是：用「奖金 ÷ 12」去查**月度税率表**，再按奖金**全额**计税。

```text
MONTH_BRK = [3000/3%/0, 12000/10%/210, 25000/20%/1410, 35000/25%/2660,
             55000/30%/4410, 80000/35%/7160, ∞/45%/15160]
tax = bonus × rate − 速算扣除数
```

> v1.1.0 修复的真实缺陷：原实现拿「奖金 ÷ 12」去比**年度**阈值（36000/144000/…），
> 档位整体偏低，96000 被算成 3%（2880 元），正确是 10%（**9390 元**），差 6510 元。
> 该缺陷由测试用例发现，`tests/calc.test.js` 留有回归断言。

### 4.4 `offerCalc(o)` → Offer 年化

```text
现金       cash   = 月薪 × 月数 + 年终奖
公积金年入 fundY  = 月薪 × 比例% × 12      （个人+公司合计进入个人账户）
综合年包   total  = cash + fundY + 期权年折算
年工时     hoursY = (40 + 周加班) × 48     （48 个工作周）
真实时薪   hourly = cash / hoursY          （只算现金，公积金不算「干出来的钱」）
年通勤     hours  = 单程分钟 × 2 × 250 / 60
```

两处刻意的取舍：

- **时薪分母用现金而非总包**：公积金和期权不是每月可支配现金流，摊进时薪会高估「这份工作干得值不值」。
- **时薪不让期权参与**：期权按 0 估值时也不亏的 Offer 才更稳，所以另设「期权按 0 算」的结论提示。

### 4.5 `taxOf(income)` → 综合所得年度个税

七级超额累进，年减除费用 6 万。用于「并入综合所得」一侧的对比。

## 5. JD 匹配算法

没有大模型，靠「词库 + 频次 + 权重」做确定性匹配。分三步：

1. **抽取**：`TECH` 词库 261 个技术词，逐个在 JD 文本中统计出现次数；同时用 `/[a-z][a-z0-9+#.\-/]{1,19}/g` 抓英文 token，出现 ≥2 次且不在停用词表的，作为补充关键词。
2. **对比**：同一套抽取跑在简历上，得到简历词频表。JD 有、简历没有 → **缺失项**。
3. **排序与输出**：缺失项按 JD 出现频次降序（出现 2 次以上大概率是面试必问点）；每个缺失项查知识库，命中则渲染「速学卡片」，未命中则套通用学习框架模板。

**为什么频次优先而不是字典序或字母序**：JD 里被反复提及的要求，通常就是团队当前最缺的能力。这个排序规则在真实 JD 上比任何启发式都稳。

## 6. 知识库结构

三层组织，目标只有一个：**任何缺失词都能看到东西，且看到的是具体内容而不是空模板**。

```
KB        66 张卡片（已有内容，含旧版浅卡片）
KB_DEEP   24 张深度卡片 —— 覆盖同名浅卡片，写满 9 个字段
KB_PATCH  10 张深度补丁 —— 只写增量字段，浅合并到已有卡片上
KB_FAM    60 张词族卡片 —— 承接词库里没有独立卡片的词
ALIAS     227 条关键词 → 卡片/词族的映射
```

合并顺序 `KB_DEEP → KB_PATCH → KB_FAM`，合并后再做一次字段归一（`d/p` → `one/mech`），
渲染层只需要认一套字段。

```js
KB['redis'] = {
  t:    'Redis',                       // 术语（标题）
  one:  '一句话本质',                    // 它到底是什么，不是定义复读
  why:  '为什么需要它',                  // 没有它会发生什么（痛点因果）
  mech: ['核心机制 1', '核心机制 2'],     // 带参数/数字，能直接开口讲
  code: ['命令 1', '命令 2'],            // 可复制，<pre> 展示
  trap: ['常见误解'],                    // 答错就掉分的地方
  qa:   [['追问', '参考答案']],          // 带答案，含追问第二层
  say:  '30 秒面试话术',                 // 第一人称，可直接背
  use:  '写进简历的句式模板',             // 与简历优化器共用同一份数据
  path: '10 分钟学习路径'
}
```

深度卡片必须同时有 `say` 与 `use`——只讲原理不给话术，用户还是开不了口；
只给话术不给写法，简历里还是写不出来。

**词族映射**解决的是长尾：`nacos` 没有独立卡片，映射到「注册中心」；
`i2c/spi/can/uart/gpio` 映射到「总线与外设」。渲染时标注「关键词：nacos → 词族「注册中心」」，
让用户知道自己在看族级知识，而不是误以为是专讲 nacos。

未收录（且无映射）的词走兜底卡片，给出四步研究清单：
从 JD 上下文找用法 → 只读官方概念节 → 抄高频题 → 准备迁移话术。
宁可给研究路径，也不编造具体 API 或参数。

## 6.1 简历体检算法

纯规则引擎，不依赖模型，因此结果确定、可断言、可复现。

**输入**：简历文本 + 可选 JD。**输出**：五维得分、问题清单、逐句改写、植入句式、简历骨架。

| 维度 | 权重 | 计算方式 |
|---|---|---|
| 量化结果 | 30 | `含量化数字的条目 / 内容条目`，60% 得满分 |
| 关键词匹配 | 25 | JD 关键词覆盖率，70% 得满分 |
| 强动词 | 15 | 含「主导/设计/落地/优化」等 24 个强动词的条目占比，50% 得满分 |
| 结构完整 | 20 | 教育/技能/工作经历/项目/自我评价 命中数 ÷ 5 |
| 表达规范 | 10 | 满分 10，每处口语词 −2、每行超 90 字 −2、无分点 −3，下限 0 |

未填 JD 时按可用满分 75 归一化到 100，避免「关键词 0 分」把总分压得没有参考意义。

**量化判断的前置处理**：先剔除 `2019-2021`、`2020 至今` 这类年份区间再判断是否含数字。
否则任何写了在职时间的简历都会被算成「有量化」，评分虚高——这个缺陷是写测试时发现的。

**逐句改写**：弱动词映射表（负责→主导、参与→承担…），命中即替换；
若该句剔除年份后仍无数字，追加「【补：量化结果…】」提示。只改动词不改事实，避免替用户编经历。

**关键词植入**：复用 JD 匹配的缺失词列表，按频次降序取前 10，
每条给可填空句式与知识库 `use` 字段的参考写法；不会的技术引导写「正在补」，不做「包装」。

## 7. 复盘分类算法

10 个类别：基础八股 / 操作系统与网络 / 数据库与缓存 / 分布式与架构 / 系统设计 /
项目深挖 / 算法手撕 / 场景与开放题 / HR 与软素质 / 其他。

分类按规则表顺序匹配关键词，先命中先归入；都不命中归「其他」。
用户可在保存时手动指定类别（`cat: 'auto'` 表示交给规则）。
导出时先按类别跨公司汇总，再按公司时间线，最后统计出现 ≥2 次的「高频薄弱点」。

## 8. 构建链与 PWA

单文件是开发形态，PWA 是发布形态，两者由构建脚本同步，避免出现「两份代码」。

```text
offer-compass.html  ──(tools/build-app.js 注入 PWA 头)──▶  app/index.html
                                                            app/manifest.webmanifest
                                                            app/sw.js
                                                            app/icon-*.png  ← tools/make_icons.py
```

- **单源**：`app/index.html` 是产物，不入手工编辑。任何改动只改源文件再构建。
- **构建即校验**：缺少任一 PWA 资源（清单/SW/图标）直接拒绝构建，线上不会出现半套 PWA。
- **缓存策略**：`sw.js` 用「缓存优先 + 网络回填 + 版本号清理」。纯本地应用没有动态接口，全部静态资源缓存后即可完整离线运行。
- **离线兜底**：导航请求失败时返回缓存的 `index.html`，而不是浏览器的断网错误页。

## 9. 降级与失败设计

| 失败场景 | 行为 |
|---|---|
| `localStorage` 不可用（隐私模式/配额满） | 保存处 `try/catch` 吞掉异常，页面照常计算；备份面板提示「保存失败」 |
| 浏览器不支持 Service Worker | 注册处判空跳过，应用功能不受影响 |
| 浏览器未提供安装入口 | 「安装到桌面」给出各平台手动安装路径，而不是静默无反应 |
| 备份文件损坏或不是本应用导出 | 明确报错并**不写入**，避免覆盖现有数据 |
| 数值为空 / 非法 | 计算前置校验并提示具体缺哪一项，而不是给出 0 或 NaN |
| 日期倒挂 | `compMonths` 返回 `-1`，界面提示「离职日期需要晚于入职日期」 |
| JD 抽不出任何关键词 | 提示「未能从 JD 中识别出关键词」，不输出空报告 |
| 复盘导出但无记录 | 提示「还没有复盘记录」，不生成空文件 |

核心原则与知识库一致：**宁可留空，也不给一个看起来正确的错数字。**

## 10. 安全与隐私边界

- 无后端、无账号、无埋点、无第三方脚本、无外部字体与图标。
- 简历 / 工资 / 面试记录**只在内存与本机 localStorage**，不产生任何网络请求。
- 备份是本地生成的 JSON 文件，去向由用户自己决定。
- 页面的对外链接只有 GitHub 仓库与 Issue 页，均为用户主动点击。
- 不代填、不代投递、不接触任何招聘平台账号。

## 11. 测试策略（三层）

| 层 | 文件 | 断言数 | 保证什么 |
|---|---|---|---|
| 计算 | `tests/calc.test.js` | 120 | 算得对：工龄、N、年终奖税、综合所得税、Offer 年化、词频、分类、知识库完整性 |
| 结构 | `tests/structure.test.js` | 35 | 点得动：onclick 函数是否存在、id 是否存在、标签与面板是否对应、关键能力入口是否都在 |
| 现场 | 页面底部「🧪 计算器自检」 | 15 | 用户不装 Node 也能当场验证，断言调用的是页面正在运行的同一份函数 |

前两层 `npm test` 一次跑完，CI 在每次 push 时执行。
计算层不是另写一套算法，而是**从 HTML 抽出内联脚本**在最小 DOM 桩上执行——测试和线上跑的是同一份代码。

## 12. 已知限制

1. **政策有时效**：年终奖单独计税政策执行至 2027-12-31；补偿规则依据现行《劳动合同法》。政策变动需人工同步。
2. **各地口径差异**：竞业补偿比例、社平工资、公积金基数上限由地方规定，页面只做提示不做判定，重大决策请核实当地人社局公布值。
3. **JD 匹配是词面匹配**：同义词、缩写、语境差异会漏判（如「消息中间件」与「MQ」）。这是无模型方案的固有限制，用「通用框架兜底」缓解，不假装解决。
4. **不跨设备同步**：这是隐私设计而非缺陷，迁移靠 JSON 备份。
5. **单文件规模**：源码集中在一个 HTML，已接近可维护上限；若继续增长，下一步应拆分为 ES 模块 + 构建打包，而不是继续堆。
